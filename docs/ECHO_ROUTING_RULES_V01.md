## 📋 文檔目的

本文檔定義 Echo 回應系統的判斷規則，確保使用者完成記錄後能抽取到最適合的回應。

**設計原則：**
- **Deterministic** - 相同輸入永遠產生相同輸出
- **Simple** - 基於選項、checkbox、completion 簡單判斷
- **No AI** - 不使用 AI、NLP、關鍵字分析
- **Fallback Safe** - 異常情況有安全回應

---

## 一、Life Flow Routing

### **資料來源**
```javascript
lifeChoice: string  // 單選 radio button
```

### **選項映射**
```
"今天沒有硬撐，很穩" → L1 安穩型
"今天有吃到好吃的" → L2 生活型  
"今天有見到重要的人" → L3 陪伴型
```

### **路由規則**

#### **規則 L-1：直接映射**
```
IF lifeChoice === "今天沒有硬撐，很穩"
THEN USE L1 安穩型回應池

IF lifeChoice === "今天有吃到好吃的"  
THEN USE L2 生活型回應池

IF lifeChoice === "今天有見到重要的人"
THEN USE L3 陪伴型回應池
```

#### **規則 L-2：未選擇 Fallback**
```
IF lifeChoice === null || lifeChoice === "" || lifeChoice === undefined
THEN USE F1 通用回應池
```

### **預期分佈**
- **L1 安穩型**: 30-40% （最常見的狀態）
- **L2 生活型**: 25-35% （生活記錄常見）
- **L3 陪伴型**: 20-30% （社交互動記錄）
- **F1 Fallback**: <5% （異常情況）

## 二、Easy Flow Routing

### **資料來源**
```javascript
easyChoice: string[]  // 多選 checkbox array
```

### **選項內容**
```
- "有去岩館"
- "有動一點身體"  
- "有練習一個小技巧"
- "有讓自己休息"
- "有觀察到新的東西"
```

### **分類定義**

#### **E1 累積型 - 動態活動導向**
**特徵：** 去岩館、動身體、練技巧
**條件：** 包含運動相關選項

#### **E2 觀察型 - 認知學習導向**  
**特徵：** 觀察新東西
**條件：** 包含觀察選項

#### **E3 恢復型 - 休息放鬆導向**
**特徵：** 讓自己休息
**條件：** 包含休息選項

#### **E4 平衡型 - 多元混合**
**特徵：** 多種類型混合選擇
**條件：** 符合多個不同類別

### **路由優先順序表**

#### **規則 E-1：單一類型判斷**
```
IF 只包含 ["有觀察到新的東西"]
THEN USE E2 觀察型

IF 只包含 ["有讓自己休息"]  
THEN USE E3 恢復型

IF 只包含運動類 ["有去岩館", "有動一點身體", "有練習一個小技巧"]
THEN USE E1 累積型
```

#### **規則 E-2：多選優先順序**
```
優先級排序（高到低）:
1. E3 恢復型 - 只要包含 "有讓自己休息"
2. E2 觀察型 - 只要包含 "有觀察到新的東西" 
3. E4 平衡型 - 包含 >=3 個不同選項
4. E1 累積型 - 其他所有情況
```

#### **規則 E-3：具體判斷邏輯**
```
IF easyChoice.includes("有讓自己休息")
THEN USE E3 恢復型
// 理由：恢復是最重要的狀態，優先回應

ELSE IF easyChoice.includes("有觀察到新的東西")
THEN USE E2 觀察型  
// 理由：認知成長值得特別回應

ELSE IF easyChoice.length >= 3
THEN USE E4 平衡型
// 理由：多元活動顯示平衡生活

ELSE
THEN USE E1 累積型
// 理由：默認為累積型，適合一般運動記錄
```

### **決策樹範例**
```
用戶勾選：["有去岩館", "有讓自己休息", "有觀察到新的東西"]
→ 包含休息 → E3 恢復型

用戶勾選：["有動一點身體", "有觀察到新的東西"]  
→ 不含休息，但含觀察 → E2 觀察型

用戶勾選：["有去岩館", "有動一點身體", "有練習一個小技巧"]
→ 不含休息觀察，>=3個 → E4 平衡型

用戶勾選：["有去岩館"]
→ 其他情況 → E1 累積型
```

### **預期分佈**
- **E1 累積型**: 40-50% （運動類選項常見）
- **E2 觀察型**: 15-25% （學習認知記錄）
- **E3 恢復型**: 20-30% （休息狀態重要）
- **E4 平衡型**: 10-20% （多元活動）

## 三、Challenge Flow Routing

### **資料來源**
```javascript
completion: string  // 完成度選項
```

### **選項值**
```
- "all"    // 全部完成
- "most"   // 大部分完成  
- "half"   // 一半完成
- "little" // 很少完成
```

### **分類映射**

#### **C1 完成型 - 高完成度**
**條件：** completion === "all" || completion === "most"
**特徵：** 完成度高，任務達成感

#### **C2 持續型 - 中等完成度**
**條件：** completion === "half"
**特徵：** 部分完成，進行中狀態

#### **C3 困難型 - 低完成度**  
**條件：** completion === "little"
**特徵：** 完成度低，遇到困難

### **路由規則**

#### **規則 C-1：直接映射**
```
IF completion === "all" || completion === "most"
THEN USE C1 完成型回應池

IF completion === "half"
THEN USE C2 持續型回應池

IF completion === "little"  
THEN USE C3 困難型回應池
```

#### **規則 C-2：異常處理**
```
IF completion === null || completion === "" || completion === undefined
THEN USE F1 通用回應池
```

### **預期分佈**
- **C1 完成型**: 35-45% （多數情況能完成大部分）
- **C2 持續型**: 30-40% （部分完成很常見）
- **C3 困難型**: 15-25% （困難情況相對少）
- **F1 Fallback**: <5% （異常情況）

## 四、Fallback Pool 設計

### **F1 通用回應池**
**用途：** 處理資料缺失、異常、舊版本相容

#### **觸發條件**
```
- lifeChoice 為空或異常值
- easyChoice 為空陣列  
- completion 為空或異常值
- 系統找不到對應回應池
- 舊資料格式不相容
```

#### **F1 通用回應池內容**
```
1. 今天留下了一些痕跡。
2. 這一天被記下來了。
3. 今天多了一些記憶。
4. 今天的頁面有了內容。
5. 這個時刻被保存下來。
6. 今天有東西被記住了。
7. 今天留下了一個片段。
8. 這一天多了一行字。
9. 今天被放進記憶裡。
10. 今天有一些被記錄下來。
```

#### **F1 設計原則**
- **最大兼容性** - 適合任何情況
- **最大留白** - 不做具體假設
- **最安全** - 不會產生違和感
- **符合憲法** - 遵循 Echo 風格標準

## 五、路由決策流程

### **主要決策流程**
```
1. 識別 Entry Flow 類型
   ├─ Challenge Flow → 使用 completion 判斷 C1/C2/C3
   ├─ Easy Flow → 使用 easyChoice[] 判斷 E1/E2/E3/E4
   └─ Life Flow → 使用 lifeChoice 判斷 L1/L2/L3

2. 檢查資料完整性
   ├─ 資料正常 → 執行對應路由規則
   └─ 資料異常 → 使用 F1 Fallback

3. 從對應回應池隨機選擇
   └─ 返回選中的 Echo 回應
```

### **實作檢查清單**
```
□ 確認 Entry Flow 類型（Challenge/Easy/Life）
□ 提取對應資料欄位
□ 執行路由規則判斷
□ 處理異常情況 Fallback
□ 從目標回應池隨機選擇
□ 記錄選擇結果（用於未來優化）
```

## 六、未來擴充規劃

#### **擴充點 A：movementNotes 文字分析**
**掛接位置：** 在基礎路由規則之後
```
基礎路由（E1-E4） → 文字分析修正 → 最終選擇

例如：
E1 累積型 + movementNotes="今天很累" 
→ 可能調整為 E3 恢復型回應
```

#### **擴充點 B：關鍵字情緒判斷**
**掛接位置：** 作為路由修正層
```
基礎分類 → 關鍵字分析 → 情緒權重調整

例如：
檢測到 "困難"、"卡住" 關鍵字
→ 傾向選擇較溫和的回應
```

#### **擴充點 C：AI 語意分類**
**掛接位置：** 作為高級路由選項
```
傳統規則 → AI 語意理解 → 智能分類

但保留：
- 傳統規則為主要路徑
- AI 為輔助判斷
- Fallback 到確定性規則
```

### **擴充原則**
- **向下兼容** - 不影響現有 MVP 功能
- **漸進增強** - 可選擇啟用智能功能
- **安全 Fallback** - AI 失效時回到確定性規則
- **性能優先** - 智能功能不影響回應速度

### **未來架構設想**

## 七、實作指南

### **開發優先順序**
1. **Life Flow 路由** - 最簡單，優先實作
2. **Challenge Flow 路由** - 邏輯簡單，次優先
3. **Easy Flow 路由** - 複雜度最高，最後實作
4. **F1 Fallback** - 安全機制，與主功能並行
5. **路由測試** - 覆蓋所有邊界情況

### **測試案例設計**
```
Life Flow:
- 正常選擇：3種選項 × 各10次 = 30次測試
- 異常情況：空值、null、undefined = 3次測試

Easy Flow:  
- 單選情況：5個選項各單選 = 5次測試
- 多選組合：重要組合測試 = 10次測試
- 異常情況：空陣列、null = 2次測試

Challenge Flow:
- 正常完成度：4個值 × 各10次 = 40次測試
- 異常情況：空值、無效值 = 3次測試

Fallback:
- 各種異常情況觸發 = 5次測試
```

### **性能要求**
- **路由決策時間**: < 10ms
- **回應選擇時間**: < 5ms  
- **總 Echo 生成時間**: < 20ms
- **記憶體使用**: 回應池預載入，避免實時讀取

## 八、監控與優化

### **數據收集指標**
```
- 各回應池使用頻率
- Fallback 觸發頻率  
- 用戶對 Echo 的隱性反應（未來功能）
- 路由決策執行時間
- 異常情況統計
```

### **優化方向**
- **回應池平衡** - 確保各池使用頻率合理
- **Fallback 最小化** - 減少異常情況
- **回應多樣性** - 避免重複回應
- **用戶體驗** - 根據數據調整路由規則

## 🔒 版本控制

### **更新原則**
- **路由規則變更** - 需要版本號更新
- **回應池內容變更** - 不影響路由版本
- **新增 Flow 類型** - 需要主版本更新
- **Fallback 調整** - 需要記錄變更原因

### **相容性保證**
- **向下相容** - 新版本支持舊資料格式
- **漸進升級** - 路由規則可以漸進增強
- **安全降級** - 異常時回到最基礎規則
